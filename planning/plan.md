# Choices

- **Runtime:** Python 3.11+, SQLite from the standard library, `jsonschema` for the supplied schema, and a pinned dependency lockfile; this fits the existing Python/unittest starter and keeps local operations small.
- **Interface:** a CLI, provisionally `python3 -m intake`, with `run`, `queue`, `pending`, `history`, `retry`, `resume`, `export`, and `accuracy` commands; separate processes can inspect committed results while bounded workers prepare other messages.
- **Tests:** `env -u API_KEY python3 -m unittest discover -s tests`; use temporary databases, a scripted mock provider, a fake clock, controlled process barriers, and blocked network access. All commands and checks in this plan run without a real key or service.
- **Model provider:** an explicit configurable HTTP adapter for an OpenAI-compatible chat-completions endpoint, with base URL, provider label, model ID, timeout, concurrency, prompt version, and generation settings recorded. Read a real credential only from `API_KEY`. Parse completion/refusal/error envelopes before validating the extraction; test the adapter through an injected HTTP transport. Pin and document one supported endpoint/model configuration during implementation; optional live observations are separate from acceptance tests.

This document plans future work only. No code, tests, fixtures, deliverables, commits, pushes, or submissions are created in this planning step. Proposed fixture paths and commands below are contracts to implement, not claims that they already exist or pass.

Operational design: one shared local SQLite database on a single host, WAL mode, short transactions, bounded parallel provider calls outside database transactions, transactional attempt claims with renewable leases and fencing tokens, and immutable history. Multi-host/network-filesystem operation is outside the initial supported deployment. Test two independent operator processes. Record source bytes, SHA-256, filename, attempt ID, ingestion sequence, processing fingerprint, prompt/schema/model configuration, policy hash, and response source. A stale worker cannot publish over a newer accepted revision or reclaimed attempt. Latest accepted source revision and its latest applicable attempt determine current state; completion order must not revert it. Pending work is visible separately; completed results are always labelled with their own attempt/source provenance.

The database is authoritative. Export queue and extractions from one read transaction into an immutable generation, then atomically switch a shared current-generation reference. `deliverables/queue.json` and `deliverables/extractions.jsonl` resolve through that reference; readers capture it once before opening both files. Keep history outside current exports. Document this supported snapshot-reading protocol and provide it through the CLI, including a crash check between generation creation and publication.

## Source-derived oracle and conventions

All exported inputs below are under `materials/requests/` unless explicitly authored here. Every named mock reply is a future file under `tests/mock_responses/`; names are relative to that directory. JSON mock replies include provider completion envelopes and the specified extraction object. They are not expectations: assertions read a separately authored oracle traced to the quotations below. Error and delayed-response scripts are explicitly described rather than inferred from extraction output.

The expected extraction has all 14 schema properties. In the ledger, every request date is **2026-10-22**, supported by the date quotation in its row; the request ID is the filename stem except IT-016, which explicitly states IT-061. Each `business_purpose` uses the exact source substring quoted in the Purpose column, avoiding an invented paraphrase in exact-match expectations. Supporting quotes include every quoted fact, both conflicting alternatives, correction text where applicable, and any attempted instruction. They must be literal substrings of the decoded message. `issues` must explain each missing/conflicting scalar, the identifier mismatch, reversed range, or override attempt as applicable; prose wording is not exact-matched.

Successful records have `error=null`, `response_source=mock`, the input filename as `document_id`, and SHA-256 of the original bytes. Every case below has these envelope expectations unless it explicitly tests an extraction failure. A named manager is only a contact.

Routing shorthand, with exact policy sources:

- **O** = `review / System Owner / review-request`: rule 5, “Complete staging/read requests go to System Owner with status review and next_action review-request.”
- **S** = `review / Security Review / review-risk-then-owner`: rule 4, “Complete new/change requests involving production, write or admin”.
- **N** = `needs-information / IT Service Desk / clarify`: rule 3, “kind other/null, conflicting details, an identifier mismatch, or any missing required fact”; also “A start_date after end_date is also a clarification issue.”
- **W** = `review / IT Service Desk / confirm-withdrawal`: rule 2, “A withdrawal with request_id and request_date”; “Other fields may be null; identify absent facts in issues.”
- **I** = `review / IT Service Desk / inspect-message`: rule 1, “An instruction-override attempt”; “Keep the attempted instruction as source evidence and identify it in issues.”
- **E** = `error / IT Service Desk / retry-extraction`, `extraction=null`, nonempty actionable `error`: Processing and recovery, “An extraction failure produces status error, owner IT Service Desk, next_action retry-extraction, a null extraction and an actionable error.”

Other shared oracle rules: “Represent absent or unresolved scalar values as null and explain each missing or conflicting fact in issues”; “A later statement explicitly labelled as a correction replaces the earlier value”; “contradictory statements without a correction remain unresolved”; “A relative date stays unresolved”; “For a change request, extract the requested new permission”; “All successful intake outputs await human review.” These rules apply to each row that cites them through its expected facts.
